# ローカルストレージの限界とは？容量・削除タイミング・安全性を徹底解説【中級者向け】

Webアプリでダークモードや入力途中の内容を覚えておきたい。そんなとき、数行のJavaScriptで使える `localStorage` は便利です。

ただし、ブラウザを閉じても残ることと、データが永久に保存されることは別です。容量には上限があり、保存処理は同期的で、ブラウザの設定やプライバシー保護の仕組みによってデータが消える場合もあります。

この記事では、localStorageの容量・削除条件・安全性を整理し、PWAを含むWebアプリでどこまで任せてよいのかを解説します。

## localStorageとは？

`localStorage` は、同じオリジンのWebページから利用できる、ブラウザ内のキーと値の保存領域です。オリジンは通常、**スキーム・ホスト名・ポート番号**の組み合わせで決まります。

```js
localStorage.setItem("theme", "dark");
const theme = localStorage.getItem("theme");
```

ブラウザやタブを閉じても原則として保存内容が残ります。一方、`sessionStorage` は基本的にタブ単位のページセッションが終了すると破棄されます。どちらもサーバーへ自動送信されるCookieとは役割が異なります。

### 保存できるのは文字列だけ

オブジェクトをそのまま保存すると、意図しない文字列になります。JSONへ変換して保存し、読み出す際に復元します。

```js
const settings = { theme: "dark", fontSize: "large" };
localStorage.setItem("settings", JSON.stringify(settings));

const raw = localStorage.getItem("settings");
let restored = null;
try {
  restored = raw === null ? null : JSON.parse(raw);
} catch {
  // 古い形式や破損データを想定して初期値へ戻す
  restored = null;
}
```

JSONに変換できない値もあるため、保存するデータの形式はあらかじめ決めておくと安心です。

## 容量の限界は約5MiBが目安

Web Storageには比較的小さな容量制限があります。一般的な目安は**オリジンごとにlocalStorageが約5MiB**ですが、実際の上限や計算方法はブラウザによって異なります。どの端末でも必ず5MiB保存できると考えるべきではありません。

ダークモードの設定なら十分な容量でも、画像をBase64で保存したり、大きなJSONや操作履歴を蓄積したりする用途には向きません。

容量超過などで書き込めない場合、`setItem()` は `QuotaExceededError` を投げることがあります。ストレージへのアクセス自体が制限される環境もあるため、失敗を想定した処理が必要です。

```js
function saveSettings(value) {
  try {
    localStorage.setItem("settings", JSON.stringify(value));
    return true;
  } catch (error) {
    console.warn("設定を保存できませんでした", error);
    return false;
  }
}
```

## localStorageは同期処理

`getItem()` や `setItem()` は同期APIです。読み書きが終わるまでJavaScriptの処理が待たされるため、大きな文字列を頻繁に扱うと画面の反応に影響することがあります。

小さな設定値なら扱いやすい一方、検索可能な大量のレコードやオフラインデータには非同期の `IndexedDB` の方が適しています。

## データはいつ消える？

localStorage自体には、Cookieのような有効期限を指定する仕組みはありません。しかし、次のような理由でデータを利用できなくなることがあります。

- ユーザーがWebサイトデータを削除した
- プライベートブラウズのセッションが終了した
- ブラウザのプライバシー保護・保存領域管理の対象になった
- ブラウザのプロファイル変更、アプリの削除、端末の初期化などで保存先が変わった
- 保存先のオリジンが変わった（例：`http` と `https`、サブドメインの違い）

**保存できたという事実は、次回も必ず読めるという保証にはなりません。**

### SafariのITPと「7日」の話

SafariのIntelligent Tracking Prevention（ITP）には、一定条件下で、スクリプトから書き込めるストレージを制限・削除する仕組みがあります。WebKitは、ユーザーの操作がない状態が7日続いたサイトのスクリプト書き込み可能なストレージについて、制限を説明しています。

ただし、これは**すべてのiPhoneのlocalStorageが7日で必ず消える**という意味ではありません。Safariでの利用状況、ホーム画面に追加されたWebアプリ、ブラウザのバージョンなどによって扱いが異なります。低容量時の削除についても、特定の保存領域が必ず先に消されると決めつけるべきではありません。

PWAだから永久保存できる、逆にPWAの方が必ず消えやすい、といった一律の説明も避けた方が正確です。

## Cookie・IndexedDB・Cache APIとの使い分け

| 保存方法 | 主な用途 | 注意点 |
|---|---|---|
| `localStorage` | UI設定、軽量な状態 | 小容量・同期処理・永続保証なし |
| `sessionStorage` | タブ内の一時状態 | ページセッション終了で破棄 |
| `IndexedDB` | 構造化データ、オフラインデータ | 非同期・容量制限や削除の可能性あり |
| `Cache API` | リクエストとレスポンスのキャッシュ | 更新・削除戦略が必要 |
| Cookie | セッション管理など | サイズ制限・送信範囲・属性設定に注意 |

IndexedDBやCache APIはlocalStorageより大きなデータに向きますが、**どちらも絶対に消えない保存先ではありません**。重要なユーザーデータは、適切な認証とアクセス制御を備えたサーバー側で管理し、必要に応じて同期・復旧できる設計にします。

## セキュリティ：認証トークンを安易に置かない

localStorageは同一オリジン上で動くJavaScriptから読み取れます。XSS（クロスサイトスクリプティング）により悪意あるスクリプトが実行されると、保存値が盗まれる危険があります。

そのため、長期間有効な認証トークン、決済情報、機密性の高い個人情報などを安易に保存しないことが重要です。認証セッションには、要件に応じて `HttpOnly`・`Secure`・`SameSite` などを設定したCookieを検討します。ただしCookieにもCSRFなど別の対策が必要です。

## 実装で意識したい3つのこと

### 1. 消えても起動できるようにする

保存値が `null` でも正常に動き、必要ならサーバーから再取得できるようにします。設定値はデフォルトへ戻せる構成が基本です。

### 2. 保存形式にバージョンを持たせる

```js
const data = { version: 1, theme: "dark" };
localStorage.setItem("app-settings", JSON.stringify(data));
```

将来のアップデートでデータ構造が変わったときに、移行や初期化の判断がしやすくなります。

### 3. 保存失敗と読み出し失敗を処理する

容量超過だけでなく、利用制限や不正なJSONにも備えます。特に入力途中のデータなどは、保存できなかったことをユーザーに知らせる設計が必要です。

## まとめ：localStorageは金庫ではなく、小さなメモ帳

localStorageは、**小さな設定を手軽に保存するための仕組み**です。約5MiBという容量の目安、同期処理、削除の可能性、JavaScriptから読み取れる性質を理解して使えば、非常に便利です。

一方、消えたら困る唯一のデータ、大きな画像や履歴、機密情報の保存先には向きません。WebアプリやPWAでは、localStorageに任せる範囲を小さくし、重要なデータは別の保存先と復旧手段を用意することが大切です。
