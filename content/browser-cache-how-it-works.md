WebサイトのCSSを直したのに、スマホでは前のデザインのまま。JavaScriptを更新したのに、古い動作が残っている。そんなとき、まず疑いたいのがブラウザキャッシュです。

ただし、 **「更新されない＝ブラウザキャッシュが原因」とは限りません。** CDNやService Worker、そもそもデプロイが反映されていない場合もあります。この記事では、HTTPキャッシュの基本と、原因を順番に切り分ける方法を整理します。

## ブラウザキャッシュとは？

ブラウザキャッシュは、取得したHTML・CSS・JavaScript・画像などのレスポンスを再利用し、通信量と読み込み時間を減らす仕組みです。キャッシュがあれば毎回すべてをダウンロードする必要はありません。

一方、更新後も古いレスポンスを再利用すると、修正が見えなくなることがあります。大切なのは、**キャッシュがあるかどうかより、いつ再利用してよいと判断されるか**です。

## 強キャッシュと弱キャッシュの違い

「強キャッシュ」「弱キャッシュ」は実務で使われる呼び方で、HTTP仕様上の正式な分類名ではありません。おおむね、鮮度が有効なキャッシュの再利用と、サーバーへの再検証を指します。

### 強キャッシュ：有効期間内はそのまま再利用

```http
Cache-Control: public, max-age=3600
```

この例では、取得してから原則1時間はレスポンスを新鮮（fresh）とみなし、通常の読み込みではサーバーに確認せず再利用できます。`Expires` でも期限を指定できますが、通常は `Cache-Control` が優先されます。

```http
Cache-Control: public, max-age=31536000, immutable
```

このような長期キャッシュは、**内容が変わるたびにURLも変えるファイル**と相性が良い設定です。ただし「必ず1年間更新されない」という意味ではありません。再読み込み方法やキャッシュ削除などによって挙動は変わります。

### 弱キャッシュ：サーバーに変更を確認する

```http
Cache-Control: no-cache
ETag: "build-42"
```

`no-cache` は「保存禁止」ではありません。**保存してもよいが、再利用する前に再検証する**という指定です。

次のリクエストでは、ブラウザが例えば以下を送ります。

```http
If-None-Match: "build-42"
```

変更がなければサーバーは `304 Not Modified` を返し、ブラウザは手元のデータを再利用します。変更があれば通常 `200 OK` と新しい内容が返ります。

`Last-Modified` と `If-Modified-Since` も同様の再検証に使われます。`ETag` と併用される場合、通常は `If-None-Match` が優先されます。

## `no-cache` と `no-store` は違う

| 指定 | 意味 | 主な用途 |
| --- | --- | --- |
| `max-age=3600` | 一定時間は新鮮として再利用できる | 更新頻度に応じた静的ファイル |
| `no-cache` | 再利用前にサーバーへ再検証する | HTML、更新頻度の高いJSON |
| `no-store` | HTTPキャッシュに保存しない | 保存自体を避けたい機密レスポンス |
| `immutable` | 新鮮な期間中は内容が変わらないことを示す | ハッシュ付き静的ファイル |

`no-store` を指定しても、すでに存在するキャッシュやService Workerの独自保存まで自動で削除されるわけではありません。

## なぜ更新が反映されないのか

### 1. CSS・JSのURLが同じで、キャッシュがまだ新鮮

例えば `/style.css` を差し替えても、ブラウザがそのURLの旧レスポンスを有効と判断していれば、再取得しないことがあります。**同じURLが常に古いというわけではなく、レスポンスのキャッシュ設定次第**です。

### 2. CDNが古いファイルを返している

CloudflareなどのCDNは、ブラウザとは別にレスポンスを保存できます。ブラウザ側のキャッシュを無効にしても、CDNから旧ファイルが届けば表示は変わりません。オリジンサーバーとCDNの両方を確認する必要があります。

### 3. Service Workerが応答を返している

PWAでService Workerを使っている場合、`fetch` イベントでリクエストを処理し、Cache APIから古いファイルを返すことがあります。**HTTPキャッシュとService Workerのキャッシュは別の仕組み**です。通常の再読み込みだけでは解消しないこともあります。

### 4. デプロイや参照先の問題

実は新しいファイルが公開されていない、HTMLが古いファイルを参照している、別の環境を見ている、といったケースもあります。キャッシュを消す前に、配信されているファイルそのものを確認しましょう。

## 更新を確実に届けるための設計

### CSS・JSはファイル名にハッシュを付ける

```html
<link rel="stylesheet" href="/assets/style.a1b2c3.css">
<script defer src="/assets/app.d4e5f6.js"></script>
```

内容が変わればURLも変わるため、古いURLのキャッシュと衝突しにくくなります。Viteなどのビルドツールが採用する定番の方法です。

クエリを使ったバージョン付けも有効です。

```html
<link rel="stylesheet" href="/style.css?v=20261106">
```

ただし、CDNやService Workerがクエリをどう扱うかによって結果は変わります。「URLを変えればあらゆるキャッシュを必ず回避できる」とまでは言えません。

### HTMLは再検証、ハッシュ付きアセットは長期キャッシュ

よく使われる組み合わせは次のとおりです。

```http
# HTML
Cache-Control: no-cache
```

```http
# 内容ハッシュ付きCSS/JS
Cache-Control: public, max-age=31536000, immutable
```

HTMLが新しいアセットURLを参照し、アセット自体は長く再利用できる設計です。HTMLまで長期キャッシュすると、新しいファイル名をブラウザが知る機会を失う場合があります。

## 更新されないときの切り分け手順

1. **公開先の確認**：新しいファイルが本当にデプロイされているか確認する。
2. **Networkパネルを見る**：対象ファイルのURL、ステータス、`Cache-Control`、`ETag`、転送元を確認する。
3. **キャッシュ無効で再読み込み**：PCのDevToolsで「Disable cache」を有効にして比較する（通常、DevToolsを開いている間の設定）。
4. **CDNを確認**：CDNのキャッシュ状態やパージの必要性を確認する。
5. **Service Workerを確認**：登録状況、制御中のページ、Cache Storageの内容を調べる。

最初から閲覧履歴やサイトデータを全削除するのはおすすめしません。ログイン状態や保存データまで失う場合があります。

## Safari・Chrome・Firefoxで違うの？

どのブラウザもHTTPキャッシュの基本的な仕組みは共通ですが、再読み込みや容量管理などの実装には差があります。Safariだけが必ず古く、Chromeなら必ず正しく更新される、といった単純な序列はありません。

また、戻る・進むで以前の画面がそのまま復元される場合は、**BFCache（Back/Forward Cache）** が関係することがあります。これは通常のHTTPキャッシュとは別の仕組みなので、区別して調べる必要があります。

## まとめ

ブラウザキャッシュはサイトを速くするための重要な仕組みです。問題はキャッシュそのものではなく、**更新頻度とキャッシュ設定が合っていないこと**にあります。

CSS・JSにはバージョン付きURLを使い、HTMLは適切に再検証させる。更新が見えなければ、ブラウザ・CDN・Service Worker・デプロイの順に切り分ける。これだけでも「直したのに変わらない」問題をかなり減らせます。
