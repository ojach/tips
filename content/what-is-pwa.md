スマホでWebサイトを開いたとき、「これをアプリみたいに使えたら便利なのに」と思ったことはありませんか。

ホーム画面に専用のアイコンを置いて、タップするとブラウザのアドレスバーがない画面で開く。場合によってはオフラインでも使える。そんな体験をWeb技術で実現する考え方が**PWA（Progressive Web App）** です。

ただし、ホーム画面にアイコンを置けるサイトが、すべて同じ仕組みで動いているわけではありません。この記事では、PWAの基本、普通のWebサイトやネイティブアプリとの違い、できることと注意点を整理します。

## PWAとは？

PWAは、**Webサイトをアプリのように使いやすくするための技術や設計の組み合わせ**です。

WebサイトなのでURLでアクセスでき、検索やリンクからも開けます。そのうえで、対応するブラウザやOSでは次のような体験を提供できます。

- ホーム画面に専用のアイコンと名前を表示する
- ホーム画面から起動したときに、ブラウザのアドレスバーを隠した画面で表示する
- 必要なデータを保存し、オフラインでも一部の機能を使えるようにする
- 対応環境では通知などの機能を利用する

すべてのPWAがこれらの機能を備えているわけではありません。どこまでできるかは、サイト側の実装と利用するOS・ブラウザによって変わります。

## 「ホーム画面に追加できる」だけでPWAなの？

ここは混同しやすいところです。

iPhoneやAndroidでは、普通のWebページでもホーム画面にリンクを置ける場合があります。**アイコンが置けることと、アプリのような表示・機能が使えることは別**です。

たとえば、ホーム画面から開いても通常のブラウザのタブで表示されるものもあります。一方、サイトに適切な設定があり、OSが対応していれば、独立したアプリのような画面で起動できます。

また、「Service Workerがなければ絶対にホーム画面アプリにできない」というわけでもありません。インストールやホーム画面追加の条件はブラウザごとに異なり、Service Workerは主にキャッシュ、オフライン対応、通知などの機能で重要になります。

## PWAを支える主な仕組み

### Web App Manifest：名前・アイコン・起動方法を決める

`manifest.json` などのWeb App Manifestは、ホーム画面に追加した際の見た目や起動方法をブラウザに伝える設定です。

```json
{
  "name": "My Web App",
  "short_name": "My App",
  "start_url": "/",
  "display": "standalone",
  "icons": [
    { "src": "/icons/icon-192.png", "sizes": "192x192", "type": "image/png" },
    { "src": "/icons/icon-512.png", "sizes": "512x512", "type": "image/png" }
  ]
}
```

`name` はアプリ名、`icons` はアイコン、`display` は表示方法を指定します。`standalone` は、対応環境で通常のブラウザUIを省いた表示を希望する設定です。

`start_url` はホーム画面から起動するURLです。`"/"` はサイトのルートを指定します。`"."` は**manifestのURLを基準に解決される相対URL**であり、ユーザーが今見ているページを自動的に指定するものではありません。ページごとに異なる起動先を用意したい場合は、manifestの配置や生成方法も含めて設計する必要があります。

### Service Worker：通信とキャッシュを制御する

Service Workerは、Webページとは別に動作し、ネットワークへのリクエストやキャッシュを扱える仕組みです。

たとえば、必要なファイルを事前に保存すれば、通信が切れたときにも一部の画面を表示できます。反対に、キャッシュの設計が悪いと、更新したはずのページが古いまま残ることもあります。

**Service Workerを登録しただけで自動的にオフライン対応になるわけではありません。** どのデータを保存し、いつ更新するかまで実装する必要があります。

キャッシュの扱いは、[PWAのキャッシュ戦略](https://tips.ojapp.app/pwa-cache-strategy/)でも詳しく説明しています。

### HTTPS：安全な環境で動かす

Service Workerなどの機能は、基本的にHTTPSのような安全なコンテキストで利用します。ローカル開発時の `localhost` などには例外があります。

公開するPWAでは、HTTPSを前提に考えるのが基本です。

## PWAのメリット

### アプリストアを経由せずに届けられる

Webサイトとして公開できるため、ユーザーはURLからアクセスできます。ホーム画面追加に対応していれば、ストアでアプリを探さずに使い始められます。ただし、追加操作の手順はiPhoneとAndroidで異なります。

### Webサイトの更新を活かせる

通常のWebコンテンツはサイト側で更新できます。アプリストアで新しいバージョンを配布する必要がない点は魅力です。

ただし、**更新が必ず即座に全員へ反映されるわけではありません。** ブラウザやService Workerのキャッシュ、端末の状態によっては古い表示が残ります。

### 繰り返し使うサイトと相性がよい

予約ページ、会員ページ、Webツール、ECサイトなど、何度も訪れるページはホーム画面から直接開けると便利です。

単なるブックマークとの違いは、アイコンの見た目だけではありません。起動方法や表示方法まで整えることで、Webサイトを日常的な道具として使いやすくできます。

## PWAのデメリット・注意点

PWAにも限界があります。

- **OSやブラウザで挙動が異なる：** Android ChromeとiPhone Safariでは、ホーム画面追加、表示、通知などの扱いが一致しません。
- **ネイティブアプリと同じ機能を使えるとは限らない：** ハードウェアへのアクセスやバックグラウンド動作には制約があります。
- **保存容量はゼロではない：** キャッシュやオフラインデータを保持するPWAは、端末のストレージを使用します。
- **キャッシュ管理が必要：** 更新が反映されない原因になることがあり、開発時には注意が必要です。

特に、PWAはコードが正しくても端末によって見た目が変わることがあります。PCの開発者ツールだけでなく、実際のスマホで確認することが大切です。

## 普通のWebサイト・PWA・ネイティブアプリの違い

| 比較項目 | 普通のWebサイト | PWA | ネイティブアプリ |
| --- | --- | --- | --- |
| 主な入口 | ブラウザ・リンク | ブラウザ・リンク・ホーム画面 | アプリのアイコン |
| ホーム画面 | リンクとして追加できる場合がある | アプリ風の起動に対応できる | 通常はインストール時に配置 |
| オフライン | 通常は限定的 | 実装次第で対応 | アプリの実装次第 |
| 更新 | Web側で更新 | Web側で更新（キャッシュに注意） | アプリ更新が必要な場合が多い |
| 端末機能 | ブラウザの対応範囲 | ブラウザ・OSの対応範囲 | OSのAPIを幅広く利用可能 |

PWAはネイティブアプリの完全な代替というより、**Webの手軽さを残したまま、必要な部分をアプリに近づける方法**です。

## どんなサイトに向いている？

たとえば、毎日使うWebツール、店舗の予約画面、会員向けサービス、繰り返し読む情報サイトなどです。

反対に、たまに一度だけ見るページなら、無理にアプリ風にする必要はありません。ホーム画面に置いてまで使いたい理由があるかどうかが、導入を考えるときのひとつの目安になります。

実際に作ってみたい場合は、[PWAの作り方](https://tips.ojapp.app/how-to-pwa/)でmanifestやService Workerの設定手順を紹介しています。

## まとめ：PWAはWebサイトをもっと身近にする仕組み

PWAは、Webサイトをホーム画面から開きやすくしたり、アプリのような表示やオフライン機能を持たせたりするための技術です。

ただし、ホーム画面に追加できることだけでPWAの機能がすべて使えるわけではありません。manifestは名前や起動方法を指定し、Service Workerは必要に応じてキャッシュやオフライン機能を担います。

最初に考えたいのは、機能を増やすことよりも「そのWebサイトを、ユーザーがどう使いたいか」です。何度も開くページなら、ホーム画面に自然に置けること自体が大きな価値になります。
