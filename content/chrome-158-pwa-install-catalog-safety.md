Chrome 158で、PWAを紹介するWebサイトの作り方が変わります。紹介ページから別のWebアプリのインストールを案内できるようになるためです。これまでは「アプリのサイトへ移動して、そこでホーム画面に追加する」という流れが中心でしたが、Web Installの仕組みを使えば、紹介ページそのものをインストールの入口にできます。

個人的には、これはPWAの見つけ方を変える可能性がある機能だと思っています。アプリを集めたカタログ、便利なWebツールのまとめ、趣味のPWA紹介ページ。今までリンクを並べるだけだったページに、インストールという選択肢が加わります。

ただし、アプリを紹介する側には実装上の条件があります。そして利用する側にも、知っておくと安心なポイントがあります。今回はChromeの公開資料をもとに、**PWA紹介サイトを作る人・使う人の両方が押さえたい注意点**を整理します。Androidでの配置上限やData URL Manifestの実機検証は、別の機会に扱います。

## Chrome 158のWeb Installで何ができる？

Web Installでは、WebページからWebアプリのインストールを開始する方法として、HTMLの`<install>`要素とJavaScriptの`navigator.install()`が用意されています。紹介ページとインストール対象のアプリが別のオリジンでも、必要な条件を満たせば対象にできます。

例えば、あるPWAのManifestが`https://app.example/manifest.webmanifest`で公開されているなら、紹介ページ側に次のような要素を置く形です。

```html
<install manifest="https://app.example/manifest.webmanifest"></install>
```

これはブラウザが表示を管理するインストールボタンです。サイト側が好き勝手に見た目を作るボタンとは性格が異なり、ブラウザ側の確認画面を通してインストールが進みます。ページを開いただけで勝手にアプリが入る機能ではありません。

JavaScriptから扱いたい場合は、次のように書けます。

```js
await navigator.install({
  manifest: "https://app.example/manifest.webmanifest",
});
```

実際のサイトでは、クリック操作から呼び出し、失敗やキャンセルにも対応する必要があります。どちらも同じWeb Installの仕組みですが、紹介サイトの規模によって使い分けが重要になります。

## 作る側の注意点：アプリ一覧に`<install>`を並べすぎない

Chromeのガイドでは、1ページに配置できる`<install>`要素の数は、ブラウザの迷惑行為対策によって制限されると説明されています。具体的な上限数は示されていません。

例えばTipsの記事で関連するPWAを1〜3個紹介するなら、`<install>`は扱いやすい候補です。ところが、数十件、数百件と並ぶアプリカタログを同じ方法で作ると、配置制限が設計上の問題になります。

大量のアプリを扱う場合、公式ガイドは`navigator.install()`を適した選択肢として挙げています。JavaScript側でボタンや一覧のUIを作れるため、インストールボタンの表示数に関する`<install>`固有の制約を避けられます。

ただし操作感は同じではありません。**別アプリをインストールする場合、`<install>`はインストール確認前の追加の権限確認を必要としませんが、`navigator.install()`では先に`web-app-installation`の権限確認が入ります。** カタログの設計では、この違いも考えたいところです。

| 比較 | `<install>` | `navigator.install()` |
| --- | --- | --- |
| 記述方法 | HTML要素 | JavaScript API |
| ボタンの見た目 | ブラウザが管理 | サイト側で設計可能 |
| 大量の一覧 | 配置数の制限に注意 | 大規模カタログ向き |
| 別アプリの追加権限確認 | インストール確認前の追加確認なし | 追加の権限確認あり |

「ボタンを置けるだけ置こう！」という発想で作ると、後から設計を見直すことになりそうです。

### PWA LABで配置上限を検証してみた

Chrome 157で実験的な機能をFlagから有効にし、1ページに`<install>`を30個配置して動作を確認しました。

24個を超えた時点で、Chromeのコンソールには次の警告が表示されました。

```text
Maximum limit of 24 permission elements has been reached.
More permission elements can be added but they will not be clickable
```

ところが、実際に操作してみると少し違う結果になりました。

| 配置数 | 検証結果 |
|---|---|
| 24個 | コンソールが示す上限 |
| 25〜29個目 | クリック可能 |
| 30個目 | クリック不可 |

**コンソールには24個が上限と表示されたものの、実際には29個目まで操作でき、30個目がクリック不能になりました。**

警告の数字と実際の操作制限が一致していないのは、興味深い挙動です。

今回の結果はChrome 157のFlag有効環境で確認したものです。Chrome 158正式版でも同じ挙動になるかは、今後の確認事項として残しています。

少なくとも、PWA紹介サイトで各アプリに`<install>`を設置する場合、配置数の制限は実際に考慮する必要があります。

## Manifestはインストール先のアプリ自身が用意する

外部のPWAを紹介するとき、ManifestのURLと`start_url`のオリジンは一致している必要があります。例えばManifestが`https://app.example/manifest.webmanifest`なら、起動先も`https://app.example/`のオリジンに属している必要があります。

ここで注意したいのがサブドメインです。`tips.ojapp.app`と`ojapp.app`は同じルートドメインを使っていますが、**Webのオリジンとしては別物**です。紹介ページが`tips.ojapp.app`で、対象アプリが`ojapp.app`なら、外部アプリを紹介する構成になります。

一方、Manifestが`ojapp.app`にあり、`start_url`だけ`tips.ojapp.app`を指す構成は、外部アプリ用のManifestとして必要な条件を満たしません。URLの見た目が似ているかどうかでは判断できない部分です。

さらにChromeのガイドでは、外部アプリのManifestはHTTPSで取得でき、認証やリダイレクトなしでアクセスでき、JSONの適切な`Content-Type`で返される必要があるとされています。PWA紹介サイトを運営するなら、登録されたURLがManifestとして正しく配信されているか確認する設計が必要です。

## `id`と`manifestid`を混同しない

OJappでPWAを扱っていると、Manifestの`id`がアプリの識別にどれだけ関わるかを意識する場面が多くあります。Web Installでもここは重要です。

対象のManifestには、安定した`id`を設定するのが基本です。`<install>`の`manifestid`属性は、対象のアプリIDを好きな値に変更する仕組みではありません。**取得したManifestから決まるIDと、指定したIDが一致するか確認するための値**です。

Manifestに`id`がない場合は、`start_url`から計算されるIDを`manifestid`に指定して照合します。アプリの識別を安定させたいなら、紹介ページ側の属性で工夫するより、アプリ本体のManifestを整える方が先です。

<figcaption class="balloon__name">アッピン</figcaption>
</figure>

## Data URL ManifestはOJappで気になる検証テーマ

OJapp FREEでは、Manifestを動的に生成する方式を使っています。そのため、一般的なHTTPS上のManifestファイルを前提としたWeb Installの説明を読むと、ひとつ気になることがあります。

**Data URL Manifestを、外部のPWA紹介ページからインストール対象として指定できるのか？**

例えば`<install>`の`manifest`属性へData URLを渡したらどうなるのか。現在のページに紐づく動的Manifestを、別ページからどう扱えるのか。これはOJapp FREEや1P1Aの設計に直接関係する疑問です。

Chromeの現行ガイドは、外部アプリのManifestについてHTTPSで到達できるURLなどの条件を示しています。Data URLの扱いについては、今回の時点では実機で確認していません。この記事では対応可否を断定せず、後日の検証項目として残します。

## 使う側の注意点：まずブラウザで試してみる

PWA紹介サイトを利用する側に、いちばん伝えたいのはこれです。

**気になるPWAを見つけたら、まずブラウザで開いて使ってみましょう。気に入ったらインストールすれば十分です。**

PWAはWeb技術を使ったアプリです。多くの場合、インストールする前からWebサイトとして機能を体験できます。使い勝手、表示速度、必要なアカウント登録、サービスの雰囲気。紹介文だけでは分からない部分を、実際に触って確かめられます。

APKファイルをダウンロードしてAndroidにインストールする方法とは、配布の仕組みが違います。PWAのインストールは、対応するブラウザがWebアプリとして登録する操作です。紹介サイトに「インストール」と書いてあっても、APKの配布サイトと同じ感覚で考える必要はありません。

ただし、**PWAであること自体は安全性の保証ではありません。** ブラウザで試すときも、URLや運営元を確認することが大切です。

### 提供元と権限を確認する

アプリ紹介サイトの運営者と、掲載されているPWAの運営者は別の場合があります。紹介サイトに載っているからといって、そのサービスが紹介サイトによって運営・保証されているわけではありません。

特にログインを求められる場合は、開いているURLが正しいかを確認しましょう。通知、位置情報、カメラ、マイクなどの許可を求められた場合も、用途に必要かを見て判断するのが基本です。

また、ホーム画面に追加できたからといって、オフラインでもすべての機能が使えるとは限りません。通信が必要な機能や、アカウントが必要な機能もあります。ここも先に試しておくと分かりやすいところです。

## PWA紹介サイトには「試す」と「入れる」の両方がほしい

個人的には、PWAのカタログにはインストールボタンだけを並べるより、**「Webで開く」と「インストールする」を並べる設計**が合っていると思います。

まず触ってみる。使い続けたいと思ったらホーム画面に置く。これはPWAの自然な使い方です。ユーザーにいきなりインストールを迫るより、サービスそのものを判断してもらいやすくなります。

将来、PWA UPのようなアプリ紹介サイトを作るなら、この考え方を軸にしたいところです。作る側にはManifestやID、配置数の制約があり、使う側には提供元や権限を確認する視点がある。その両方を考えたカタログなら、ただアプリを大量に並べるだけのページより面白いものになるはずです。

### Chrome 158で外部サイトのPWAインストールに成功

Chrome 158で、別ドメインにあるPWAを`<install>`からインストールできることを確認しました。

検証には、Microsoft Edgeのデモサイトで公開されているManifestを使用しました。

```html
<install manifest="https://microsoftedge.github.io/Demos/pwa-install-element/manifest.json"></install>
```

このコードを`ojapp.app`のテストページに設置したところ、Chromeのインストール画面が表示されました。[テストページ](https://ojapp.app/install-test/)

画面にはインストール対象のアプリ名と提供元のドメインが表示され、通常のインストール操作へ進める状態になりました。

**PWA紹介サイト側にアプリ本体を置かなくても、外部サイトのManifestを指定することでインストール画面を呼び出せます。**

これはPWA紹介サイトを作るうえで、かなり重要な確認結果です。

### `<install>`の配置制限は単純な先着順ではなかった

以前、Chrome 157のFlag有効環境では、コンソールに24個という上限警告が表示される一方、29個目までクリックでき、30個目が反応しないという結果を確認していました。

ところが、Chrome 158で多数の`<install>`を並べて再検証すると、さらに興味深い挙動が見つかりました。

例えば、25個目と26個目ではインストール画面が表示されないのに、32個目では表示されるケースがありました。

つまり、**先頭から24個だけが有効になり、それ以降がすべて無効になるという単純な仕組みではありませんでした。**

| 検証項目 | 結果 |
|---|---|
| コンソールで示された上限（Chrome 157） | 24個 |
| Chrome 157での初回確認 | 29個目まで操作可能、30個目は不可 |
| Chrome 158での再検証 | 25・26個目が反応せず、32個目は反応するケースを確認 |
| 有効になる要素の決定条件 | 未特定 |

Chrome 157での結果も、配置数だけでなく、どの要素が有効になっていたかを調べる必要がありそうです。

現時点では、**大量に配置した場合、どの`<install>`が操作可能になるかを配置順だけでは判断できない**というのが実測結果です。

PWA紹介サイトで各アプリのカードに`<install>`を並べる場合、この挙動には注意が必要です。

### Data URL Manifestは`<install>`で使用できなかった

OJapp FREEでは、JavaScriptでManifestを動的生成し、Data URLとして`<link rel="manifest">`に設定する方式を使用しています。

この方式が`<install>`でも利用できるか、Chrome 158で検証しました。

結果は、**Data URL Manifestを`<install>`の`manifest`属性に直接指定してもインストールできませんでした。**

通常の`<link rel="manifest">`で利用できるData URLが、`<install>`でも同じように使えるとは限らないわけです。

今回確認した`<install>`のManifest取得条件は、次のとおりです。

- `https://`で取得できるManifestであること
- リダイレクトなしで取得できること
- 認証なしでアクセスできること
- JSONのMIMEタイプで配信されていること
- Manifestと`start_url`が同一オリジンであること

OJapp FREEのようにData URL Manifestを生成する仕組みを、外部PWA紹介サイトからそのままインストールする用途には利用できませんでした。

**今回の検証では、外部サイトのHTTPS Manifestは利用できましたが、Data URL Manifestは利用できませんでした。**

PWA紹介サイトを作る場合、Manifestの公開方法も設計上の重要なポイントになります。
