Webサイトを更新したのに古い画面が出る。ホーム画面に追加したアプリのアイコンが変わらない。ブラウザのデータを削除したらログインまで解除された。

こうした問題は、まとめて「キャッシュの問題」と呼ばれがちです。でも、実際には保存されているものも、その管理者も違います。

私自身、PWA LABでオフライン動作を検証したり、OJappでService Workerを使わずにホーム画面アプリを作ったりしてきました。その中で重要だと感じたのは、**アプリとして起動する仕組みと、データを保存する仕組みを分けて考えること**です。

## ブラウザは何を保存しているのか

まず、キャッシュとWebストレージは同じものではありません。Webサイトが利用する代表的な保存の仕組みを整理してみます。

| 仕組み | 主な用途 |
| --- | --- |
| HTTPキャッシュ | HTML・CSS・画像などの通信を減らす |
| localStorage | 設定や入力内容などを文字列で保存する |
| sessionStorage | タブのページセッション中に状態を保持する |
| IndexedDB | 構造化されたデータを保存する |
| Cache API | リクエストとレスポンスを明示的に保存する |
| Cookie | セッション識別やサーバーとの状態共有 |

HTTPキャッシュは、ブラウザがHTTPヘッダーなどに従って管理します。一方、localStorageはJavaScriptから読み書きする保存領域です。画像をキャッシュすることと、ユーザーが選んだテーマカラーを保存することでは、目的が違います。

例えば、テーマカラーや小さな設定を保存するならlocalStorageで十分な場合があります。ただし、同期的に動作し、容量にも制限があります。上限は環境によって異なり、数MB程度を目安にしても、必ずその容量を使えるとは限りません。書き込みに失敗する場合も考えておく必要があります。

大きなデータや複雑な検索が必要ならIndexedDBが候補になります。どちらも永続的なバックアップではありません。ユーザーによる削除やブラウザの保存ポリシーによって失われる可能性があります。

## Service Workerは通信をどう変えるのか

Service Workerは、ページとは別に動作するイベント駆動のJavaScriptです。HTTPSなどの安全なコンテキストで登録し、制御対象のページから発生する通信を`fetch`イベントで扱うことができます。

通常のページでは、ブラウザがHTTPキャッシュやネットワークを使ってレスポンスを取得します。Service Workerが制御している場合は、その処理に独自の判断を加えられます。保存済みのレスポンスを返したり、通信に失敗したときだけ代替ページを返したりできるわけです。

ただし、登録するだけで全ページがオフライン対応になるわけではありません。何を保存し、いつ使い、いつ削除するかを実装して初めてキャッシュ戦略になります。Cache API自体はService Worker専用でもありません。

### キャッシュ戦略はコンテンツに合わせて選ぶ

| 戦略 | 動作 | 向いている用途 |
| --- | --- | --- |
| Cache First | 保存済みのレスポンスを優先 | バージョン付き画像・CSSなど |
| Network First | 通信を優先し、失敗時に保存済みデータを使う | 更新頻度の高い記事やフィード |
| Stale While Revalidate | 保存済みデータを先に返し、裏で更新する | 多少古くても利用できるコンテンツ |

PWA LABではCache FirstやNetwork Firstなどの違いを整理してきました。Cache Firstはオフラインに強い一方、更新管理を間違えると古い内容を返し続けます。速さだけを理由にすべてをCache Firstにするのは、私は避けたいところです。

ログイン後の個人情報や決済画面などは、公開画像と同じように保存すべきではありません。キャッシュ対象とユーザーの切り替え、ログアウト時の処理まで考える必要があります。

## オフライン対応はどこまで必要か

オフライン対応といっても、アプリの全機能を通信なしで動かす必要はありません。記事を読む、入力途中の内容を残す、通信できないことを知らせる。それぞれ必要な仕組みは違います。

PWA LABでService Workerの配置場所を変えて検証した際、`/lab/sw.js`からLAB内のページをオフラインで開けました。一方、より深い`/lab/app/{token}/sw.js`を使った検証では、上位の`/lab`を同じようにオフラインで開くことはできませんでした。

Service Workerのデフォルトのscopeはスクリプトのあるディレクトリです。通常、その上位のページは制御できません。サーバーの`Service-Worker-Allowed`ヘッダーで許可範囲を広げる方法もありますが、Manifestの`scope`とは別の設定です。また、Cache APIにURLを保存できることと、そのページのナビゲーションを制御できることも別です。

この検証から私は、サイト全体を一つのService Workerで覆うより、必要な機能やディレクトリごとに制御範囲を考える方が管理しやすいと感じています。ただし、scopeを分けても同じオリジンのCache Storageが自動で分離されるわけではないので、キャッシュ名や削除処理にも注意が必要です。

## 更新したのに古い画面やアイコンが出る理由

更新が反映されないとき、まず何が古いのかを切り分けます。HTMLなのか、CSSや画像なのか、Service Workerが返すレスポンスなのか、それともホーム画面に保存されたアイコンなのか。

HTTPキャッシュでは`Cache-Control`や`ETag`などが関係します。Service Workerを使っている場合は、Cache Storageの内容だけでなく、新しいWorkerが待機状態になっていないかも確認します。古いWorkerが開いているページを制御し続けている場合があるからです。キャッシュ名のバージョン管理や不要になったキャッシュの削除も重要です。

ホーム画面のアイコンはさらに別です。ブラウザで新しい画像が表示されても、すでに追加したアイコンが同時に更新されるとは限りません。私がアイコンを変更して経過を観察した実験でも、Web上の画像と端末に登録されたアイコンを分けて考える必要がありました。

こうした見えない保存状態を便宜上「シャドウキャッシュ」と表現することもありますが、標準化されたCache APIの種類を指す言葉ではありません。原因が確認できない段階で、すべてをService Workerのせいにするのは避けたいところです。

## キャッシュ削除とサイトデータ削除は違う

SafariやChromeでキャッシュを削除するときは、削除対象を確認してください。画像やファイルだけを削除する操作と、CookieやWebストレージを含むサイトデータの削除では影響が異なります。後者ではログイン状態や保存した設定が失われる場合があります。

ホーム画面からWebアプリを削除する操作も、すべてのサイトデータを消す操作と同じとは限りません。Safariとホーム画面アプリの保存領域や削除時の扱いはOS・ブラウザ・追加方式によって変わるため、一律に共有される、あるいは完全に分離されると考えない方が安全です。

開発時には、まず通常のブラウザ表示とホーム画面からの起動を比較し、開発者ツールで通信やService Workerの登録状態、保存済みデータを確認します。必要なデータを退避してから、問題のある保存領域を消す方が原因を追いやすくなります。

## PWAにService Workerは本当に必要なのか

私がOJappで採用しているのは、JavaScriptでWeb App Manifestを動的に生成し、ページやディレクトリ、サイトをホーム画面の入口にする方法です。ホーム画面への追加とstandalone表示のために、独自のService Workerを必須にはしていません。

対応するブラウザでは、Service Workerなしでもホーム画面への追加やアプリ風の起動が可能です。ただし、インストールUIの条件はブラウザや方式によって異なります。Manifestだけで独自のオフライン処理が実現するわけでもありません。

ここが私の考えるPWA設計の分かれ道です。オンラインで最新の情報を見せることが目的なら、まず通常のWeb通信とManifestで成立するかを考える。通信が途切れても使える必要があるなら、その機能に合わせてService Workerや保存処理を設計する。

## まとめ：何を保存するかより、なぜ保存するか

キャッシュは通信を減らし、ストレージは状態を残し、Service Workerは通信の扱いを変えられます。Manifestはアプリの名前やアイコン、起動方法などを定義します。それぞれ役割が違います。

私はPWAを作るとき、技術を全部盛り込むことより、必要な機能を選んで挙動を把握できることを重視しています。オフライン対応が必要なら設計する。不要なら無理にキャッシュを増やさない。

ホーム画面から開いたときに、ユーザーが期待する情報を使えること。そのためにどの保存方法が必要なのかを考えるのが、キャッシュ設計の出発点だと思います。
